Chapter 1 · Start here

One handbook, three levels of meaning.

Every chapter starts with the practical idea, connects it to cost or risk, then exposes the implementation. Read straight through or use the contents to solve the problem in front of you.

For everyone

Plain language, exact clicks, safe defaults, and explanations of unfamiliar terms.

For decision makers

For builders

Data contracts, process boundaries, source files, artifacts, tests, and extension points.

What this project is

LoRA Fine-tune Studio is a local, single-user Streamlit application for supervised fine-tuning of causal language models. It downloads models and datasets from Hugging Face, or accepts a local CSV/JSON/JSONL dataset, then trains a parameter-efficient adapter on an NVIDIA CUDA GPU.

What it is not

Not a hosted trainer

GitHub hosts the source. Training happens on the Windows computer running the app.

Not an RLHF system

The current implementation trains SFT adapters. DPO, RLHF and RLAIF are learning context, not app features.

Not an Ollama converter

The playground talks to models already installed in Ollama. It does not import the newly trained adapter.

Outcome

A completed run produces a small adapter, tokenizer files, metrics and the exact training configuration under .runs/<run-id>/output/.

Chapter 2 · Mental model

Change less of the model.

A large model already knows language. Fine-tuning changes its behavior with examples. PEFT methods avoid retraining every weight.

The five objects that matter

ObjectPlain meaningIn this app
Base modelThe general-purpose model you start with.A Hugging Face causal-language-model repository such as Qwen/Qwen3-0.6B.
TokenizerTurns text into numeric tokens the model processes.Loaded from the same model repository and saved with the adapter.
DatasetExamples of the behavior you want.Hugging Face dataset or uploaded CSV, JSON or JSONL.
TrainingRepeatedly measures error and adjusts learnable weights.TRL SFTTrainer with PEFT and optional evaluation split.
AdapterThe small learned difference layered onto the base model.Saved under the run's output/adapter directory.
The training signal pathSelect a stage to see what crosses that boundary.
Examples

Rows demonstrate the answers, tone or format the model should produce. Better examples usually matter more than aggressive settings.

LoRA and QLoRA

LoRAQLoRA
What changesSmall trainable low-rank matrices.The same low-rank matrices.
Base model in memoryUsually 16-bit.4-bit NF4 with double quantization.
VRAMHigher.Lower; default recommendation here.
Trade-offSimpler numerical path.More quantization complexity for much better memory efficiency.

The code uses LoRA rank 16, alpha 32, dropout 0.05 and targets all linear layers. QLoRA adds BitsAndBytes 4-bit NF4 loading; both use the same adapter configuration.

How SFT, DPO, RLHF and RLAIF differ

SFT learns from correct examples. DPO learns from chosen/rejected answer pairs. RLHF trains a preference or reward signal and then optimizes a policy. RLAIF uses AI-generated feedback instead of only human judgments.

This repository implements SFT only. Adding a preference method requires new dataset contracts, trainer configuration, evaluation and UI controls; selecting it is not currently possible.

Chapter 3 · Choose the right tool

Fine-tuning is not the first answer to every problem.

Use the cheapest intervention that produces reliable behavior. Fine-tuning is strongest when many examples express a stable pattern.

NeedStart withWhy
A better instruction or output formatPromptingFast, reversible, and requires no training.
Current private facts with citationsRAGKnowledge stays outside the weights and can be updated.
Consistent tone, schema, workflow or domain behaviorSFT/LoRAExamples can teach a repeated behavior compactly.
Choose preferred answers among plausible alternativesDPO or RLHFPreference data expresses relative quality; not supported here.
Do not fine-tune secrets into weights

Removing a training file does not remove memorized content. Keep personal, licensed and confidential data out unless governance explicitly permits it.

Chapter 4 · Prepare the machine

Install once. Launch by double-click.

The launcher prepares Python and locked dependencies automatically. Training still requires a compatible NVIDIA GPU and current driver.

Requirements

  • Windows 11 x86-64.
  • NVIDIA CUDA GPU; at least 6 GB VRAM is recommended.
  • Internet access for first setup and Hugging Face downloads.
  • Enough disk for the base model, dependency cache, dataset, checkpoints and adapter.
  • Ollama only if you want the separate local-model playground.

Fast path

  1. Get the repository

    Use GitHub's Code → Download ZIP, or clone it with Git. Extract it to a normal writable folder.

  2. Set the Hugging Face token

    Create a read token for downloads. Use a write token only if you will push adapters.

    PowerShell · persistent user variable
    [Environment]::SetEnvironmentVariable("HF_TOKEN", "hf_your_token", "User")

  3. Double-click the launcher

    Open Launch LoRA Studio.cmd. First launch installs uv, Python 3.12 and locked project dependencies. The console closes after the app becomes healthy.

  4. Use the browser

    The app opens at http://localhost:8501. Closing the browser tab does not necessarily stop the background server.

Manual developer launch

PowerShell
uv sync --group dev
uv run streamlit run streamlit_app.py
Token safety

The app reads HF_TOKEN from the process environment. It does not save the token inside run configuration, logs, the HTML handbook or repository files.

Chapter 5 · Guided lab

Complete a small training run.

Use the included sample and smallest preset first. The goal is to validate the whole pipeline before spending hours on real data.

  1. Confirm the hardware panel

    CUDA should be detected. Note GPU name, VRAM, RAM, free disk and BF16 support. Without CUDA, the app allows exploration but disables local training.

  2. Select the model

    Enter Qwen/Qwen3-0.6B. A repository-root URL such as https://huggingface.co/Qwen/Qwen3-0.6B also works.

  3. Upload the sample dataset

    Choose examples/sft_sample.jsonl. The app stores an upload by content hash and previews its rows.

  4. Inspect before training

    Confirm the detected format and columns. Fix mapping errors now; training cannot compensate for incorrect examples.

  5. Choose QLoRA

    QLoRA loads the base model in 4-bit form. It is the conservative choice for local GPUs.

  6. Choose Smoke test

    This preset uses 512-token sequences, up to 100 samples, 20 steps, accumulation 4 and no evaluation split.

  7. Start and watch

    The UI starts a separate worker. Status refreshes every two seconds; expand Training log for raw output.

  8. Compare responses

    After completion, enter one prompt. The app generates once with the quantized base model and once with the same base plus your adapter.

Success means pipeline health, not model quality

A smoke test proves that downloads, data, CUDA, training, artifacts and inference work together. Use a held-out evaluation set before claiming an improvement.

Chapter 6 · Dataset engineering

The examples are the product specification.

A clean small dataset can beat a large contradictory one. Each row should demonstrate the behavior you want at inference time.

Supported sources

  • Hugging Face dataset repository ID or HTTPS repository-root URL.
  • Uploaded .csv, .json or .jsonl, up to 200 MB.

Supported shapes

Conversational JSONL
{"messages":[
  {"role":"user","content":"Explain LoRA simply."},
  {"role":"assistant","content":"LoRA trains small adapter matrices..."}
]}
Plain text JSONL
{"text":"A complete training example as one text sequence."}
Prompt and completion JSONL
{"prompt":"Write a support reply:","completion":"Thanks for reporting this..."}

Quality checklist

  • Every answer is correct enough to imitate.
  • Formatting matches the intended production output.
  • Duplicate and contradictory rows are removed.
  • Important cases and failure cases are represented.
  • Evaluation examples are separated from training examples.
  • Licenses allow model training and downstream use.
  • Personal and confidential data has an approved basis for use.
What the normalization code does

A chosen text column is renamed to text. Prompt/completion columns are mapped into canonical prompt and completion fields. If max_samples is set, the dataset is shuffled with the configured seed before selection.

Evaluation is skipped when disabled or when the dataset has fewer than ten rows. Otherwise train_test_split uses the evaluation ratio and seed.

Chapter 7 · Training controls

Start conservative, then change one variable.

Presets bundle sensible values. Advanced controls exist for deliberate experiments, not random tuning.

PresetSequenceEpochsLimitAccumulationEvaluation
Smoke test512120 steps / 100 rows4Off
Standard10242No fixed limit8On
Quality20483No fixed limit16On
Maximum length

More context costs more memory and compute. The validated range is 128–8192 tokens.

Learning rate

Controls update size. Too high destabilizes training; too low may learn little.

Epochs

Passes over the data. More is not automatically better; overfitting can copy examples.

Batch and accumulation

Accumulation simulates a larger effective batch across several smaller GPU batches.

Gradient checkpointing

Saves VRAM by recomputing intermediate values, trading speed for memory.

Seed

Makes shuffling and splitting more repeatable. GPU training may still have nondeterminism.

Hardware recommendations encoded in the app

Detected VRAMConservative maximumMode
Below 6 GB1B parametersQLoRA
6–9.9 GB3B parametersQLoRA
10–15.9 GB7B parametersQLoRA
16 GB or more13B parametersQLoRA

These are warnings, not capacity guarantees. Context length, batch size, architecture, driver overhead and other processes also consume VRAM.

Chapter 8 · Job operations

The browser supervises; the worker trains.

Training runs in a separate process so Streamlit reruns do not destroy it. Durable JSON status and logs connect the two processes.

Training-job lifecycleSelect a state to see the available action.
Queued

create_run writes config.json and an initial status.json inside a unique twelve-character run directory.

Run directory

.runs/<run-id>/ ├── config.json # worker input; never contains HF_TOKEN ├── status.json # state, progress, PID, metrics, errors ├── training.log # worker stdout and stderr └── output/ ├── checkpoint-*/ # resumable trainer checkpoints ├── adapter/ # PEFT adapter and tokenizer ├── metrics.json └── training_config.json

Cancellation and recovery

Cancel first asks the process to terminate, waits up to ten seconds, then kills it if necessary. Resume works only when a checkpoint exists. Only one live worker is allowed; the job manager checks stored PIDs before creating another run.

Chapter 9 · Evidence

A lower loss is not the same as a better product.

Measure the behavior users care about on examples the model did not train on.

Built-in comparison

The app loads the base model in four-bit form, generates a deterministic response, releases GPU memory, then loads the same base with the completed PEFT adapter and generates again. This is a useful spot check, not a statistically valid evaluation.

Evaluation ladder

  1. Pipeline: did the run finish and save valid artifacts?
  2. Offline quality: does the adapter improve a held-out test set?
  3. Regression: did safety, general ability or formatting get worse?
  4. Human review: do domain experts prefer the result?
  5. Operational: are latency, memory and failure rate acceptable?
  6. Business: does the improvement change cost, time, conversion or risk?
QualityTask accuracy, rubric score, preference win rate
SafetyHallucination, leakage, harmful or disallowed behavior
OperationsLatency, GPU memory, throughput, failure rate

Publishing to Hugging Face

Enable Hub upload, provide a destination repository and use an HF_TOKEN with write permission. The trainer pushes the adapter model and tokenizer, not a merged full-model copy.

Ollama playground boundary

The app calls Ollama's local /api/tags and /api/generate endpoints. It lists and tests models already installed in Ollama. Converting or importing the trained PEFT adapter is a separate workflow not implemented here.

Security boundaries

  • Only Hugging Face repository-root IDs or HTTPS URLs are accepted; arbitrary download URLs are rejected.
  • Remote model code is disabled with trust_remote_code=False.
  • Model loading requires safetensors.
  • Uploads are type-checked, size-limited and saved by content hash.
  • Run IDs reject traversal characters.
  • JSON status updates use temporary files and atomic replacement.
  • The Hugging Face token is read at runtime, not serialized into run state.

Why training uses another process

Streamlit reruns the script whenever controls change. A child process isolates long-running GPU work from that lifecycle. Files provide simple durable coordination without a database or message broker, which matches the app's local single-user scope.

Chapter 12 · Pilot responsibly

Define value before buying GPU hours.

A fine-tuning pilot succeeds when it changes a measurable workflow, not when training loss merely goes down.

Good pilot candidates

  • A repeated task with stable inputs, outputs and quality criteria.
  • Enough approved examples to show the desired behavior.
  • A baseline prompt or model to compare against.
  • Domain reviewers who can score held-out outputs.
  • A deployment path capable of loading the base model and adapter.

Cost map

CostWhat drives itControl
PeopleData cleaning, labeling, review and governanceStart with one narrow task and a written rubric.
ComputeModel size, tokens, epochs, experimentsUse QLoRA and smoke tests before full runs.
RiskBad data, leakage, licenses, regressionsApproval gates and held-out evaluation.
OperationsServing base weights plus adaptersBenchmark target hardware before rollout.

Four-stage pilot

  1. Baseline

    Write 30–100 representative test cases. Score the unmodified model and best prompt.

  2. Dataset proof

    Build a small reviewed training set. Run the smoke preset and inspect failures.

  3. Controlled experiment

    Train one standard configuration. Change one variable per later run and retain exact configs.

  4. Go/no-go

    Compare quality, safety, latency and full operational cost against the baseline and agreed threshold.

Production boundary

This repository is an educational local trainer, not a multi-user production platform. It has no role-based access, audit service, remote job queue, distributed training or production model registry.

Chapter 14 · Reference

Terms without the fog.

Adapter

Small learned weights applied on top of a specific base model.

Checkpoint

Intermediate training state that can resume an interrupted run.

Epoch

One pass through the selected training dataset.

Gradient

Signal describing how learnable weights should change to reduce loss.

Inference

Using a trained model to generate an answer.

Loss

Training objective measuring mismatch with expected examples.

PEFT

Parameter-efficient fine-tuning: train a small subset instead of every weight.

Quantization

Represent weights with fewer bits to reduce memory and often speed loading.

VRAM

GPU memory holding weights, activations, gradients and optimizer state.

Frequently asked questions

Does the Hugging Face API key pay for training?

No. The token authenticates downloads and optional uploads. Training compute runs on your local NVIDIA GPU.

Can I train without a GPU?

Not with the current training path. The UI may open, but train() requires CUDA.

Is QLoRA always better than LoRA?

No. QLoRA primarily solves memory pressure. LoRA avoids four-bit base-weight quantization but needs more VRAM.

Can I paste any download URL?

No. For safety, model and dataset inputs accept Hugging Face repository IDs or repository-root HTTPS URLs only.

Can Ollama run my completed adapter?

Not automatically. The included Ollama panel only tests models already installed in Ollama.

Where is my trained result?

Open .runs/<run-id>/output/adapter. Keep the matching base-model ID and revision with the adapter.
